# Demo walkthrough: approval to authorized email

This is a reproducible operating guide with explicit gates, not a statement that the clinical sequence has already completed. Latest [review readback](../../kb/exports/live-review-ui-readback.json) recorded 21 pending items, zero approvals and an empty published clinical release. No email receipt is recorded.

1. **Start local app/workers** using [setup](setup.md), initially in no-send preview. Open the configured origin. Workers poll persisted state; browser refresh alone does not run them.
2. **Reviewer sign-in:** open `/review`, use the dedicated local reviewer credentials. If absent, a trusted operator must provision the reviewer/registry. Doctor or hospital cookies do not grant this role.
3. **Inspect and personally review a few research items:** filter Lung, open each exact version, follow sources, inspect claims/passages, population and unknowns. A real human records their note and attestation, then uses **Approve exact version** or rejects. Approval is blocked until that person actually performs review; the agent must not approve clinical evidence for a demo. Changed/rejected versions need remediation/new review.
4. **Preview and publish:** select the explicit canonical candidate set and cutoff on `/review`, preview its included/excluded items/errors, then explicitly publish with the reviewer's publish permission. Review acknowledgment alone is not publication. Verify nonzero included clinical items and canonical release receipt. Empty release is valid but cannot produce a clinical briefing. This is the present content blocker.
5. **Doctor sign-in:** open `/auth` with the synthetic Lung doctor from `demo-credentials.local`. Bootstrap normally creates completed onboarding/stated details but no consent; inspect the actual current state rather than assuming it.
6. **Link and consent:** in My profile/onboarding link the account's assigned doctor code (normally DR-1001) with the doctor's consent. The doctor, not staff, owns this action. Relinking does not reuse old snapshots.
7. **Hospital publication:** sign in at `/hospital` using staff credentials, choose that assigned doctor, load the built-in demo panel or [synthetic aggregate JSON](../../fixtures/synthetic-hospital-aggregate.json). Review/authorize and use **Publish to Databricks**. Wait for acknowledged snapshot/revision. Failure is unconfirmed; recover with the same request ID rather than claiming success. Only aggregates leave the hospital browser.
8. **Generate and confirm profile:** worker processes the persisted queued job. In My profile inspect generated suggestions, select the focus to retain and confirm the current version. If failed, inspect safe status/configuration and use supported retry after its delay; staff cannot confirm. Edits/uploads supersede old confirmation.
9. **Await matching:** local worker consumes the confirmed profile/current snapshot and reviewed release, then persists a ranked package. Inspect reasons/cohort values. These are relevance cohorts; exact applicability stays unknown. Empty or stale packages cannot be used as fresh evidence.
10. **Generate/inspect briefing:** newsletter worker claims the package, verifies hosted model metadata, selects reviewed claim IDs and validates exact citations/content. With no send configuration, inspect the **Preview — no email sent** under My profile's briefing/email preferences. It is cached canonical preview state, not a library publication.
11. **Read full article and sources:** source URLs appear in preview text. Canonical `/library/newsletters/$id` and `/library/articles/$id` views become available only after publication. Current code requires send-ready configuration/subscription for that publication, so the library portion is blocked in preview mode. Once published, open the article and numbered original sources; a source link is not a license to reproduce full text.
12. **Subscribe and send only to the authorized test recipient:** complete Gmail/recipient/HTTPS prerequisites in [setup](setup.md), open the exact HTTPS origin and subscribe in My profile. Enabling the send-ready worker may automatically promote a current frozen preview; the UI also offers **Publish this validated briefing**. Worker rechecks inputs and atomically publishes library plus queued outbox, then Gmail transport runs independently. `provider-accepted` is acceptance only. This step is blocked until explicit recipient/sender authorization, HTTPS and OAuth exist; no send was performed for packaging.
13. **Verify actual receipt:** the authorized human opens their recipient inbox, checks sender/subject and working owner-scoped article/source links, and records actual receipt separately. Gmail acceptance, sent-folder reconciliation and Pub/Sub notifications cannot substitute for inbox observation. No receipt claim is currently supported by the packaged evidence.

## Cached and offline fallback

`npm run preview:newsletter` generates deterministic fictional HTML/text at `artifacts/newsletter-preview/preview.html` and `preview.txt` with a verification sidecar: offline fixture, no clinical publication, zero email sends. It is safe for layout demonstration and must be introduced as a **synthetic cached preview**. It is not a reviewed clinical newsletter. This command overwrites that local preview directory; preserve a prior receipt elsewhere privately if needed.

To pre-generate a real clinical demo preview, the actual human first approves/releases evidence, the doctor confirms inputs, and preview workers generate a valid result. The durable job retains its frozen result and provenance; later promotion revalidates current profile/snapshot/release and reuses that result. A changed input can supersede the cache. Published newsletters remain in the canonical library; show their actual generation date/version rather than claiming a fresh inference. Do not edit fixture approval fields, fabricate provider responses or mark an email received to bypass a blocked step.
