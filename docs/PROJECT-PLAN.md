## Design issues to resolve before implementation

- Profiling and evidence are separate concerns: the profiler needs onboarding taxonomy and normalization rules, not unbounded clinical retrieval. Clinical evidence belongs in the reviewed KB used for matching and briefing.
- Use canonical population IDs rather than display labels. The supplied brief already mixes labels such as “ES-SCLC after 1L chemo-IO” and “Extensive-stage SCLC after first-line chemo-immunotherapy.” Normalize cancer subtypes under Lung so exact string comparisons do not discard lung items.
- Each patient aggregate needs an explicit denominator and population definition. Categories overlap and must not be forced to sum to 100%. Do not multiply independent marginals to invent intersection sizes.
- A cohort percentage is an exact applicability estimate only when it matches the evidence eligibility definition. PD-L1 level alone does not establish untreated, nonsquamous disease. Otherwise label it as a potentially relevant cohort or report eligibility as unknown.
- A typed doctor code is a demo lookup mechanism, not proof of authorization. Production linkage requires verified ownership; browser users must not enumerate other doctors' aggregate records.
- The patient-link step must support skipping or declining: the brief calls sync opt-in even though the link-step consent checkbox is required. Require consent only when linking.
- Validate all clinical content surfaces, including digest, short summary, coverage descriptions, flags and funding. The supplied JSON contract currently attaches claim IDs only to body paragraphs.
- Claim-ID validation proves citation presence and permitted references, not that a paraphrase is entailed by its source. Human-reviewed claims and constrained drafting remain necessary; automated semantic verification is outside the stated demo scope.
- Server code, not generated prose, should set applicability values and ranking reasons. Pin profile, patient-mix, KB, prompt and model versions to each generation run.
- Preserve the four jobs' data-store boundaries. Make generation idempotent, publish atomically after validation, and ensure failed attempts do not mark items as delivered.
- Audit seeded/precomputed demo actions honestly; do not imply an ingestion, human review or live sync actually ran when it did not.
- Audio preference may be captured during onboarding; audio generation is outside the current demo scope.
